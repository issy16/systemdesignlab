      act 1 · continuous integrationci

      CI: merge small changes often, and a robot checks every one

      Same team, new rule: push small changes to main several times a day. Every push wakes up a robot (a server somewhere) that merges it, builds it, and runs the tests within minutes. Try both buttons.

      Illustrative numbers, but the shape is real: the longer you wait to merge, the bigger and riskier each merge gets.

      CI in one line

      Merge small changes into main often, and a robot builds and tests each one so problems show up in minutes, not on merge day.

      The “I” means integration: combining everyone's code. It's “continuous” because it happens all the time instead of once at the end.

      act 2 · continuous delivery / deploymentcd

      CD: same robot, longer pipeline

      CI stopped at “tests pass.” CD keeps going: the robot packages the app, puts it on a staging server (a private copy of the real site), and then it goes to production, the site real users see. The one question left: does a human press a button first?

      Continuous Delivery

      Every passing change is ready to ship. A person decides when.

      The two CDs, settled

      Continuous Delivery: every passing change is ready to ship, and a human presses the button. Continuous Deployment: there's no button, and passing changes go straight to users.

      Both need CI underneath. CD without good tests just ships bugs faster.

      The big reveal: a pipeline is just a trigger (“when someone pushes”) + a list of commands (the same ones you'd type yourself) + a borrowed computer to run them on. GitHub Actions, GitLab CI, Jenkins and CircleCI are all the same idea, just different robots reading different file formats.

      Why any of it exists
      A problem found minutes after you write it takes minutes to fix. Found three weeks later, it takes days. CI/CD makes “minutes later” the default.
