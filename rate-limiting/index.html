The token bucket

Each bucket holds up to B tokens and refills at R tokens per second. Every request spends one token. No token means the request is rejected right away with 429 Too Many Requests, so the server never has to do that work. Numbers are simulated.

    The one difference

    A single shared limit protects the server but punishes everyone for the bot's behavior. A limit per user (per account, API key or IP) protects the server and keeps the bot's behavior the bot's problem.

    Rate limiting in one line

    Cap how many requests each client can make in a time window, and reject the extra ones cheaply with a 429 before they cost real work. The bucket size allows short bursts; the refill rate sets the long-run limit.

    What
    Rate limit
    A cap on requests per client per time window. Extra requests get a fast 429 instead of using up server capacity.
    
    
    How
    Token bucket
    Bucket size = how big a burst is allowed. Refill rate = the sustained limit. Simple, cheap, and the most common algorithm.
    
    
    Who
    Per client
    Key the bucket by user, API key or IP so one heavy client can't use up everyone's allowance.
    
  
    
  
    The tradeoff
    Limits that are too tight block real fans at exactly the busiest moment, and limits that are too loose don't protect anything. Allow realistic bursts, limit per client, and tell clients when to come back (Retry-After).
