    TTL only

    Every copy expires after a fixed time. Simple, and works with any cache, but fans can see an old answer for up to the full TTL. Long TTL means less load and more staleness, short TTL means the opposite.

    Delete on write

    When the data changes, delete (or update) the cached copy. Reads stay fast and fresh. But every code path that changes the data has to remember to do it. This is cache invalidation.

    The one difference

    A cache is a copy. The real question isn't “is it fast?” but “how wrong can the copy be, and for how long?” TTL limits how long. Invalidation removes the copy the moment it's wrong.

    The whole page on one screen
    
  
    
    
    What
    Caching
    Keep a copy of an answer so you don't recompute or refetch it. Fewer database queries, faster pages.
    
    
    Where
    Edge caching
    Keep the copy in a CDN close to the fan, so hits skip the trip to your servers entirely. Only for data that's the same for everyone.
    
    
    When it's wrong
    Invalidation
    Delete or update the copy when the data changes, and use TTLs as a backstop. Decide how stale each kind of data is allowed to be.
    
  
    
  
    The tradeoff
    Every cache trades freshness for speed. A seat count can be a few seconds old on the concert page, but the checkout must always ask the database. Cache what can be slightly wrong, never what must be exactly right.
