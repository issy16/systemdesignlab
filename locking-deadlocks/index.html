Optimistic locking
Assume conflicts are rare. Don't block anyone; instead, check at save time that the record hasn't changed (a version number). If it has, reject the save and let the user retry. Cheap when conflicts are rare.

    
Pessimistic locking
Assume conflicts will happen. Lock the record before editing, so others wait their turn. No rejected saves, but people wait, and a forgotten lock blocks everyone.

    The one difference
    A deadlock needs a cycle: A holds what B wants while B holds what A wants. Databases detect the cycle and kill one transaction. You prevent it by making every transaction take locks in the same order (for example, lowest id first). Then the second one simply waits instead of grabbing the other lock.

    Check at save
    Optimistic
    A version column. UPDATE … WHERE version = 1; 0 rows means someone else saved first. Best when conflicts are rare.
    
    
    Lock first
    Pessimistic
    SELECT … FOR UPDATE inside a transaction. Others wait. Best for short, contended operations like seat inventory.
    
    
    Wait forever
    Deadlock
    Two transactions each hold a lock the other needs. Prevent it with a consistent lock order and short transactions; retry when the database aborts one.
    
  
    
  
    The tradeoff
    Optimistic locking never blocks but pushes conflicts back to users or retry code. Pessimistic locking avoids conflicts by making people wait, and every lock you take is a chance to deadlock. Most web apps use optimistic locking for edit forms and short pessimistic locks for hot counters.
