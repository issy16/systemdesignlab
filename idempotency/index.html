    The one difference

    Without a key, every request looks like a new purchase, because the server can't tell a retry from a second order. With an idempotency key, the app sends the same unique key with every attempt for one order. The server charges the first time, saves the answer, and returns that saved answer for any repeat.

    Idempotency in one line

    An operation is idempotent if doing it twice has the same effect as doing it once. Payments aren't idempotent on their own, so you make them idempotent with a key.

    The whole page on one screen
    
  
    
    
    Why
    Repeats happen
    Double-clicks, retries after timeouts, lost responses, queue redeliveries. Your server will see the same request twice.
    
    
    How
    Idempotency key
    One unique key per operation, sent with every attempt. The server stores key → result and replays the result for repeats.
    
    
    Where
    Anything with side effects
    Payments, orders, emails, seat reservations, webhooks. GET, PUT and DELETE are meant to be idempotent already; POST is not.
    
  
    
  
    The tradeoff
    You pay with a little storage (a key table with an expiry, often 24 hours) and an extra lookup per request. In return, retries become safe, and you can't build reliable retries (page 9) or queues (page 8) without that.
