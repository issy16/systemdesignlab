N+1 in one line
1 query to get the list, then N more, one per item, usually hidden inside a loop or an ORM's lazy loading. Fetch related data in bulk instead.






  
lab · the connection poolpool of 10

  
Every query needs a connection. There aren't many.

  
Opening a database connection is slow (about 30 ms here: network handshake, login, setup). Encore's database plan also allows only 20 connections in total. A connection pool opens a few connections once and lends them out. A request borrows one, runs its queries, and gives it back. If none are free, the request waits.

    The one difference
    Without a pool, every request opens its own connection: slow, and a traffic spike blows past the database's limit. With a pool, requests borrow from a fixed set: fast, and the database is protected. When the pool runs out, requests wait their turn.

    The bug
    N+1 queries
    One query for the list, plus one per item. Invisible with test data, painful with real data. Look for queries inside loops.
    
    
    The fix
    Fetch in bulk
    A JOIN, or the ORM's eager loading (include, select_related, includes). 2 queries instead of 101.
    
    
    The guard
    Connection pool
    Reuse a fixed set of open connections. Faster requests, and the database never sees more connections than it can handle.
    
  
    
  
    The tradeoff
    A bigger pool lets more requests run at once, but it can't go past what the database allows, and every app server has its own pool. Fix slow queries first: they hold connections longer and drain the pool.
