Sharding, partitioning

One database can't hold every order. So which order goes where?

EncoreThe orders table no longer fits on one machine, so Ana splits it across 4 database servers called shards. A rule decides which shard each order lives on. Pick the rule badly, and adding a 5th shard means moving almost everything, or one shard melts while the others sit idle.

Which shards does a query have to ask?

Try this

    Partitioning

    Splitting one big table into pieces by a rule, for example one piece per month. The pieces can all live in the same database; queries for one month only scan that piece.

    Sharding

    Partitioning where the pieces live on different machines. Now you can grow past one server, but the app (or a proxy) must know which shard to ask, and queries across shards get expensive.

    The one difference

    With hash mod N, changing N changes almost every answer, so adding one shard moves most of the data. Consistent hashing puts shards on a ring; a new shard only takes over the keys next to it, so only about 1 in N keys move.

    Split
    Partitioning
    Break a big table into pieces by a key. Faster queries and easy cleanup (drop an old month), still one database.
    
    
    Spread
    Sharding
    Put the pieces on different servers to grow past one machine. The shard key is the most important decision.
    
    
    Grow
    Consistent hashing
    Adding or removing a shard moves only about 1/N of the data, instead of nearly all of it.
    
  
    
  
    The tradeoff
    A good shard key spreads load evenly and matches your most common queries. Hashing spreads load but makes range queries ask every shard; ranges keep related data together but create hot spots. Sharding is hard to undo, so try indexes, caching and replicas (pages 2, 5, 14) first.
