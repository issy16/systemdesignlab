Try this

    1997
    HTTP/1.1

    One request at a time per connection. Browsers open about 6 connections per site and queue the rest.

    2015
    HTTP/2

    One TCP connection, many requests at once (multiplexing), compressed headers. But TCP still delivers bytes in order, so one lost packet stalls every request.

    2022
    HTTP/3

    HTTP over QUIC, which runs on UDP. Streams are independent, so a loss only delays its own stream, and the connection and encryption are set up in one round trip.

    The one difference

    HTTP/2 removed the queue: many requests share one connection instead of waiting for a free one. HTTP/3 removed what was left in the way: TCP's in-order delivery (head-of-line blocking, page 22) and the extra round trips of separate TCP and TLS handshakes.

    The whole page on one screen
    
  
    
    
    Many at once
    Multiplexing
    HTTP/2 and HTTP/3 send many requests over one connection. No more queueing, no more 6-connection limit.
    
    
    Independent
    QUIC streams
    HTTP/3's streams don't block each other on loss. Biggest win on lossy mobile networks.
    
    
    Faster start
    Fewer round trips
    QUIC combines connecting and encrypting into one round trip (zero when resuming). Matters most when the server is far away.
    
  
    
  
    The tradeoff
    Upgrading is mostly free speed, enabled in your CDN or web server. Costs: some networks block UDP (browsers fall back to HTTP/2), QUIC uses more CPU than TCP today, and debugging tools are younger. Tricks from the HTTP/1 era (bundling everything, domain sharding) matter much less now.
